# scsi3 design guide

This guide covers how scsi3 is meant to be used and the reasoning behind its design. Before adding a command or structure, look at the most up-to-date examples and follow the same patterns. Right now those are `scsi_mmc/features/`, `scsi_mmc/commands/get_configuration.rs`, and `scsi_mmc/commands/read_toc_pma_atip/` for a command that's generic over its response.

The crate is fragmented at the moment. Some modules predate the patterns below and haven't been brought up to date yet, so check a module against this guide before copying from it.

## What scsi3 is

- **A strict implementation of the SCSI-3 standards that optical drives use:** SAM (`core`), SPC (`spc`) and MMC (`mmc`).
  - Each directory (`scsi_core`, `scsi_spc`, `scsi_mmc`) is named after the crate it would become if scsi3 were split up.
  - `docs/references.md` lists the standard each one follows.
- **Commands and responses only, no I/O.** scsi3 builds CDBs and parses responses. The transport owns the buffers, their sizes and the residual counts.
- **It models what the spec says, not what particular drives do.** Drive quirks are the application's job (see `docs/quirks.md`). That's one reason responses are references into the caller's buffer: the application can inspect or fix the exact bytes a response was read from.
- **It shows the caller what's there rather than guessing.** The library can't tell why data disagrees with itself. The drive may be misbehaving, the response may have been cut short, or the caller may have passed the wrong bytes. So it returns what's present, keeps the evidence visible, and saves errors for responses it can't read at all.
- **Restrictions:** `#![no_std]` and `#![forbid(unsafe_code)]`. `alloc` is linked, but the goal is to stop needing it.
- **The public API follows the spec's structure and names.**
  - Types and accessors are named after the spec's tables and fields.
  - The spec's abbreviations go in `#[doc(alias = "...")]`.
  - Parsing machinery that has no counterpart in the spec stays private.

## Zero-copy parsing

- **Responses are zerocopy casts over the caller's buffer.** They are `#[repr(C)]` structs deriving `FromBytes` (or `TryFromBytes`, see below), `KnownLayout`, `Immutable` and `Unaligned`.
  - `parse` reads a length field, or the field that selects a layout, and casts, so parsing is O(1). Accessors decode the bits when called.
  - Nothing is copied, so a reference aliases the buffer, and a write through a `*_mut` accessor shows up everywhere. The caller decides when to copy.
  - **A response is a view over `buf`, not proof of what the device sent.** Bytes the device didn't send, such as an untrimmed buffer's tail or padding a transport adds (quirk 2 in `docs/quirks.md`), are read like any others. `parse` guarantees only that every byte of `buf` is either in the response or in `rest`. Trimming `buf` to the transferred count, and comparing that count with the length field, is the application's job. Docs describe what a response holds, not what the Drive sent.
- **Layouts keep every byte of the spec's table**, reserved bytes included (`_reserved`, `_bytes9_11`), so `size_of` matches the spec.
- **Multi-byte fields are `U16`/`U32<BigEndian>`**, or newtypes over them. Every type is `Unaligned`, so the `CastError::Alignment` match arms are `unreachable!`.
- **Value newtypes follow one shape** (e.g. `ProfileNumber` in `scsi_mmc/profiles.rs`):
  - They are `#[repr(transparent)]` over the big-endian integer.
  - They have const `from_u16`/`into_u16` methods, not derive_more `From`/`Into`, which aren't const.
  - Values the spec names are associated consts.
  - Debug prints hex with the spec's `h` suffix, e.g. `ProfileNumber(0008h)`.
- **Layout fields are private.** They are read through `#[inline] pub const fn` accessors, with the `bit!` macro for single bits (`scsi_core/util.rs`).
- **Bits that decide what the bytes are belong to the type.** Bytes with the wrong ones aren't that structure: a feature descriptor is only a Profile List descriptor if its Feature Code is 0000h, and three bytes of the ATIP are only a Special Information 1 if their ID bits are 101. So the layout derives `TryFromBytes`, and a cast of other bytes fails with a validity error. There's no fallback reading: correcting a drive that sets them wrong is the application's job.
  - A whole field is a single-variant enum (`FeatureDescriptor<F>` in `features/mod.rs`).
  - Bits within a byte are an enum of every byte that matches, generated by `byte_pattern!` (`scsi_core/validity.rs`), until zerocopy has custom validators. Fields of these types are read with `as u8`, as `bit!` does.
  - These types are `pub`, since zerocopy's `KnownLayout` derive names a struct's last field type in a public associated type. They're declared in modules that aren't public, so they stay out of the API: generic ones such as `Msb0` in `scsi_core/validity.rs`, and the rest in a private `mod bytes` beside the structs that use them (`device_models/cd/atip/`).
  - A field that only informs is never enforced, even one that says whether another field is valid. It's read through an accessor, and the field it gates through one that returns `None` when it isn't valid (`CdRAtip::additional_information_1`).

## Commands

- **Traits:** a command is a struct holding the CDB inputs. It implements `Command<OpCode<N>>` (`as_cdb`) and `ReadCommand` (`response_len`, `parse`) from `scsi_core/mod.rs`.
- **Generic or not:**
  - If a CDB field changes the response layout, make the command generic over the response, using sealed traits.
  - If it doesn't, keep the command non-generic with a private enum.
- **Named constructors:** name each constructor after what it requests, whether the command is generic (`ReadTocPmaAtip::{formatted_toc, pma, …}`) or not (`GetConfiguration::{all, current, single}`). For a generic command, unique names also let the response type be inferred.
- **`parse` returns `(&Response, &[u8])`:** the response, plus every byte of `buf` that wasn't read into it, as in zerocopy's `*_from_prefix`. Nothing is discarded: a partial entry that a typed tail can't hold is left at the start of `rest`.
- **A field that selects the layout** (the DDCD bit, Disc Type and Disc Sub-Type of the ATIP):
  - Each reading is its own layout, whose types accept only the values that select it, so bytes can't be cast as a reading they don't describe.
  - Readings that share a shape are one generic layout, with a type parameter for the part that varies and an alias per reading (`CdAtip<S1>`, with `CdRAtip` and the CD-RW aliases). A reading with a different shape is its own struct (`DdcdAtip`).
  - Every value of the field selects a layout, reserved values included (`CdRwReservedAtip`). Only bits that no reading allows, such as wrong ID bits, leave the bytes unreadable.
  - A part that a reading reserves is a byte array with no accessor.
  - `parse` reads the field to pick the layout, then casts as it. What it returns is still open (see "Open questions").
- **`parse` fails only when `buf` can't hold the response's fixed part** (`TruncationError`), **or when the bytes aren't the structure the layout describes** (a validity error, see "Zero-copy parsing").
  - The error comes from the cast's `CastError::Size` arm, not a separate length check. Compute `elems` so it always fits once the fixed part does. When `buf` can't hold the length field, 0 stands in for it, so `elems` is 0 and the cast reports the truncation (`pma.rs`).
  - `expected` is the length of the fixed part: `size_of` for a sized layout, or the header's constant for a layout with a variable-length tail.
  - A length field never causes an error. It only marks where a variable-length tail stops when `buf` is longer than the response, and a fixed-size response doesn't use it. Whether it matches what the device sent is for the application to judge, through the field's accessor.
  - Other fields are shown, not checked. A format code the layout doesn't expect is for the caller to act on (`StandardInquiry::response_data_format`).

## Spec revisions

- **The last revision that describes a version defines it.**
  - The draft revisions (e.g. mmcNrNNx) are working drafts. Some of them changed a version's layout without bumping the version number.
  - Model the latest description, and leave a `// NOTE:` about the earlier shape (`features/formattable.rs`).
- **Fields that a later revision made obsolete:**
  - Keep the explicit fields from the current spec.
  - Offer the old reading through an extra accessor (`features/bd_read.rs`).
  - When the obsolete field selects the layout, the old reading is its own layout instead (`DdcdAtip`), and the current spec's layouts accept only the field's current value, with no accessor for it.
- **Say what you can't verify.** The user doesn't have every draft revision. `docs/notes.md` links the archived T10 drafts.
- **Comment tags:**
  - `// NOTE:` for spec history and discrepancies.
  - `// TODO:` for work left to do.
  - `// CONFIRM:` for behavior to check on real hardware.

## Trait, inline and derive conventions

- **Trait bounds:** a trait requires only what the library itself needs. Generic code adds its own bounds (`<F: Feature + fmt::Debug>`). Registries and marker traits are sealed.
- **Constants:** use associated consts, not methods. A method implies the value isn't constant.
- **`#[inline]`:** put it on non-generic public accessors, so they can inline across crates. Leave it off generic functions, `Debug::fmt` and private functions.
- **Derives:**
  - Sized layouts: `Clone, Copy, PartialEq, Eq, Hash` plus Debug.
  - DSTs: `PartialEq, Eq, Hash` plus Debug.
  - No `Default`, since `FromZeros::new_zeroed` exists. No `Ord` on layouts.
  - Equality and hashing compare all the bytes, reserved ones included.
- **Debug:**
  - It prints the decoded values the accessors return, not the raw fields (`debug_fields!` in `scsi_core/util.rs`).
  - Write list formatting inline with `fmt::from_fn`, not through a helper type.

## Open questions

- **A claimed-length accessor on every response.** It would return the length field plus the offset it counts from: the total number of bytes the device claims the response holds.
  - **For:** an application checks a response by comparing that claim with the transferred count and with Allocation Length.
    - Equal to the transferred count: consistent.
    - Greater, with the transfer filling Allocation Length: Allocation Length was too small, so re-issue with a larger one. Length fields aren't cut by Allocation Length.
    - Greater with a shorter transfer, or less than the transfer: the device or transport disagrees, and the application has to look into it.
    - Where each length field counts from is spec knowledge that differs by format: 2 bytes for READ TOC/PMA/ATIP, 4 for GET CONFIGURATION, 5 for INQUIRY. Without the accessor, every application re-derives it for each format.
  - **Against:** it has no counterpart in the spec, and "parsing machinery that has no counterpart in the spec stays private" (see "What scsi3 is").
- **What ATIP's `parse` returns.** Until it's settled, the ATIP format has no `ReadCommand` (the TODOs in `read_toc_pma_atip/atip.rs` and `mod.rs`).
  - It names one of seven layouts. An enum with a variant per layout would borrow the response, but `ReadTocPmaAtip<R>` names its response type as a marker, which would then need `'static`.
  - A cast can fail on size or on validity. `ReadCommand::Error` has no lifetime, so a validity error can't borrow `buf` (`ValidityError::map_src` can drop it). Whether each layout gets its own error variant or they share one is open.
  - When `buf` can't hold the bytes that select the layout, something has to decide which layout's size `TruncationError::expected` reports. An earlier design used the smallest layout's.
